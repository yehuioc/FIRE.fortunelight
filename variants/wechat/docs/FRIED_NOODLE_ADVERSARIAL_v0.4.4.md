# “酒吧点炒面”式对抗测试 — V0.4.4

## 测试思想

不再只攻击 `0 / -1 / NULL / 超大数`，而是模拟**完全合理、但超出开发者预设路径的真实行为**。目标是找到“程序没崩，但产品给出了错误含义”的问题。

## 已直接修复

1. **系统基准污染统计跨度**：起始自由本金是系统基准收入，不应因为日期较早就把账本自动成本的观察期拉长。
2. **出生前交易**：2000 年出生的用户补记 1990 年支出，旧版会把成本摊到 1.3 万多天；现在模型忽略且 UI 阻止新增。
3. **配置半提交**：设置写成功、账本写失败时，旧版会出现“保存失败但一半参数已生效”；现在使用回滚日志保证逻辑一致。
4. **后台 RAF 停止**：页面进后台时，动画/静态快照不能等待一个可能永远不会再触发的 requestAnimationFrame。
5. **删除最早记录导致巨大重算却无解释**：现在历史页明确显示统计起点、观察跨度与自由时间如何被重算。

## 验证为原公式的既定行为，不修改

- 账本自动模式下，用户什么都不做只过一天，`统计天数` 会 +1；若没有新增支出，日均成本会下降，自由天数可能自然上升。这直接来自最初设计的“累计支出 ÷ 从首笔有效真实记录到今天的天数”，因此不作为 bug 修复。

## 需要产品校准的真实世界语义

以下事件当前都可以被用户“合理地”记进收入/支出，但会破坏自由模型的含义：

- **公司垫付 ¥1000 后全额报销**：净储蓄不变，但账本自动模式会把日均支出抬高。测试样例中自由天数 78 → 53。
- **自己的两个账户之间转账 ¥5000**：净储蓄不变，但如果记成一笔支出 + 一笔收入，自由天数 78 → 23。
- **消费已经逐笔记过，又把信用卡还款记成支出**：同一消费被重复计入生活成本，样例 198 → 88 天。
- **借款到账记成收入**：负债并不是新增净财富，但当前模型会把它当可购买自由时间的净储蓄；样例 100 → 600 天。
- **退款记成收入**与“撤销原支出”在账本自动模式下并不等价：样例相差 15 天自由。

这不是简单加一条 if 能正确解决的问题。必须先定义产品账本的语义：它究竟是“所有现金流账本”，还是“只记录真实新增财富与真实生活消耗的 FIRE 模型账本”。
